# Portal Capture for Android

## Build from a fresh checkout

Install Android Studio with Android SDK 36 and JDK 17. Set `JAVA_HOME` to JDK 17 and configure the SDK through Android Studio or an ignored `local.properties` file. The committed Gradle wrapper downloads the pinned Gradle distribution and verifies its SHA-256 checksum; no pre-existing Gradle cache is required.

From this directory, run `./gradlew testDebugUnitTest assembleDebug` on macOS/Linux or `.\gradlew.bat testDebugUnitTest assembleDebug` on Windows. To bundle the hosted server, add `-PportalBaseUrl=https://portal-capture-studio.vercel.app`. Device tests additionally require an emulator or supported Android phone. Local settings, credentials, signing keys, caches and build outputs are excluded from Git.

The online build uses `https://portal-capture-studio.vercel.app` automatically, including background uploads and shared links. The website and Python stitch worker are both hosted on Vercel; this computer does not need to run localhost. Existing tokens, drafts, and cached panoramas survive installation. See `../../deploy/vercel.md` for the initial free-plan limits and `../../scripts/build-online-app.ps1` for rebuilding the hosted app. Development builds without a bundled URL still expose the manual website-address field.

## Tour builder

Signed-in users start in **Your tours**. Open **Edit** for Rooms, Editor, Connections, and Style. Finished captures enter their matching tour draft automatically; removing a room records its capture ID so refreshing does not add it back. Import 2:1 panoramas through **Import 360°**. Aim the centre marker to add or reposition points; choose a room link and **Save & place return link** to position the return doorway in its destination.

Tour drafts, upload checkpoints, map positions, and private cached media live in Room database version 3. Migrations preserve existing originals and panorama downloads. Actions save locally, and WorkManager synchronises signed-in account-owned drafts and resumable uploads. Conflicts pause automatic saving until the owner loads the server draft or explicitly replaces it; a local recovery draft remains available. Undo/redo keeps 50 editor actions per session. Offline editing works for downloaded tours; new server tours and publishing need a connection.

Images and logos accept JPEG, PNG, and WebP. Videos accept H.264 MP4 with optional AAC audio. Every file is limited to 50 MB; unsupported codecs are rejected without transcoding. **Preview** uses saved room views, visible points, branding, and local media. **Publish** updates a separate public revision; later private draft edits do not change it. Sharing uses the configured Portal server address, so internet sharing requires an internet-accessible server URL. The Connections screen is an editable room graph, not a floor plan.

The backend extension is recorded in `supabase/tour-editor.sql`. Public storage access covers only assets referenced by the current published revision, excluding original capture photos and hidden point media. Existing web-editor saves preserve branding, positions, capture history, and point attachments. The public browser viewer displays logos and image/video cards.

The Supabase advisor also reports pre-existing issues outside this editor: a security-definer `owner_analytics_rollup` view and mutable search path on `set_updated_at`. These were not changed by this feature; see [view guidance](https://supabase.com/docs/guides/database/database-linter?lint=0010_security_definer_view) and [search-path guidance](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable). The established public tour/asset lookup functions intentionally remain callable by visitors and enforce published-revision boundaries. Previously issued signed media links retain their expiry after unpublishing; fresh public-tour and media-signing access is denied immediately.

Validation: `testDebugUnitTest assembleDebug assembleDebugAndroidTest`, the migration device test, and opt-in `TourEditorIntegrationTest` with instrumentation argument `tourIntegration=true`. The live tests use the phone's signed-in account, create unpublished disposable tours, and cover offline persistence, media upload, a resumed six-megabyte chunk, conflicts/recovery, publication isolation, and unpublishing. They require the existing `v` panorama on the test S22. Do not run the camera instrumentation test as part of this editor check.

The launch screen is the new Portal Capture flow. It signs in to the same account as the local Portal website, lists tours, guides ARCore capture from a fixed point, stores original calibrated JPEGs in app-private storage, and uploads them through resumable TUS transfers scheduled by WorkManager. Completed panoramas appear in the website's Capture inbox after the Python stitching worker runs.

After all 15 targets are captured, upload and server stitching start automatically. The capture review shows upload and processing progress and opens the finished panorama when its download completes. Saved captures include **View panorama**. The native OpenGL viewer supports dragging, pinch zoom, zoom buttons, and reset, with a wider 95° default field of view. Finished panoramas are stored privately on the phone for offline viewing. The website and stitching worker must be reachable for new panoramas to be built; closing the app does not cancel queued processing. Database version 2 adds the panorama path through a migration that preserves original photos and resumable uploads.

Build a debug APK with `.\gradlew.bat assembleDebug testDebugUnitTest`. Install `app/build/outputs/apk/debug/app-debug.apk` on an ARCore-capable device. For local testing, enter the website address `http://<computer-LAN-IP>:3000` on a phone or `http://10.0.2.2:3000` in an emulator. Start the website with `npm run dev -- --webpack --hostname 0.0.0.0` and run `scripts/start-worker.ps1` from the repository root. A release build accepts HTTPS only.

The **Open archived local tours** action exposes prototype tours and panorama imports. Its older guided capture entry is disabled because its local blend was a prototype; use the new launch screen for capture and the web editor for publication. Real camera movement, ARCore tracking stability, and image quality require a physical supported phone for validation.
