# Portal online deployment

Paid alternative for a persistent worker: one Railway project with two services, using the existing Supabase project. The current initial setup instead uses [Vercel Hobby](vercel.md). On Railway, the public website/API runs in `portal-web`; the Python stitcher runs continuously in `portal-worker`. The phone can capture and sync over Wi-Fi or mobile data without this computer being on. Downloaded tours still work offline.

This preparation does **not** create paid services. A Railway account, a suitable plan, and a real HTTPS domain are still required. Railway's Hobby plan currently has a US$5 monthly minimum including US$5 usage; usage beyond that costs extra. Panorama processing is CPU/RAM intensive, so this is not a fixed US$5 total. Review [current plans and metered pricing](https://docs.railway.com/pricing/plans) and configure a spending limit before deploying. The free/trial RAM limits are unsuitable for assuming reliable full-resolution stitching.

## Deploy

1. Create/sign into Railway. From this checkout, `npx --yes @railway/cli@5.68.0 login` uses Railway's browser sign-in. No credentials need to be pasted into chat.
2. Create a Railway project with two empty services named `portal-web` and `portal-worker`. Keep both services' source roots at `/`. Select a nearby European region, one worker replica, and disable service sleeping for the queue-polling worker. Start with capacity for 4 GB RAM and 2 vCPU on the worker, then measure an actual 15-photo capture and adjust; this is an initial sizing estimate, not a measured guarantee. The website can start with a smaller allocation. Do not attach a public domain to the worker. Temporary stitch files are discarded; Supabase holds originals and results, so no persistent disk is required.
3. Generate a Railway HTTPS domain for the web service (target port `3000`). Run `./scripts/prepare-online.ps1`; it emits separate clean web and worker source folders with their own `railway.json`. These packages contain no `.env`, worker password, Android files, or private local panorama previews. Normal project source uploads also have `.railwayignore` and Docker builds have `.dockerignore` as additional protection.
4. Configure variables using `./scripts/configure-online.ps1 -ProjectId <Railway-project-UUID> -PortalUrl https://<generated-domain>`. It copies only allowlisted values from the existing private environment files through stdin. The web service receives the Supabase URL, publishable key, and public origin; the worker receives the URL/key plus its restricted worker email/password. No service-role key is needed. Values remain runtime variables; they are not baked into the images. This command requires an authenticated Railway CLI and never triggers deployment itself.
5. Upload each prepared folder using `npx --yes @railway/cli@5.68.0 up <folder> --path-as-root --project <project-UUID> --service portal-web` (then `portal-worker`). Both use Docker. Wait for both deployments to succeed; web readiness checks `/api/v1/health`. Confirm worker logs say `Portal stitch worker started` and have no authentication/queue errors. `deploy/railway-web.json` and `deploy/railway-worker.json` are also usable as each service's custom config path for future Git deployments. CLI source uploads do not require a GitHub repository.
6. In the existing Supabase Auth URL configuration, change Site URL to the public origin and allow only the required production callback/recovery URLs. Do not replace tables, buckets, or accounts. Verify login and a password-reset email return to the deployed website.
7. Run `./scripts/build-online-app.ps1 -PortalUrl https://<generated-domain> -Install` with the S22 connected. The helper first checks the live Portal health endpoint, then builds the fixed online URL into Android and installs over the existing app. Existing account tokens, drafts, and photos remain on the phone. Hosted builds hide the website-address field, ignore previous LAN addresses, and use the same URL for background work and shared links. Development builds without `portalBaseUrl` retain manual addresses.

## Acceptance before switching off the computer

Use the live deployment to sign in with the existing account, load tours, upload media, capture a room, and observe it reach **ready** through the hosted worker. Verify branded preview and publish/share, then unpublish the disposable tour. Stop the local website and local worker only after the hosted worker has completed a capture successfully. Disconnect the phone from the home Wi-Fi and repeat loading/sync on mobile data. Public tour URLs must use the generated HTTPS origin, not localhost or a LAN IP. Missing configuration returns `503` at the health endpoint and must fail the web deployment check.

The image uses Next.js standalone output and a non-root Node process. The Python image runs as a restricted OS user and connects to the existing worker account. A worker restart can leave a two-minute queue lease; the durable queue can reclaim it afterwards. Retain one worker instance initially. Original capture photos and unpublished media remain governed by the existing Supabase access rules.

Reference: [Railway Dockerfiles](https://docs.railway.com/builds/dockerfiles), [configuration](https://docs.railway.com/config-as-code/reference), [public HTTPS networking](https://docs.railway.com/networking/public-networking).
